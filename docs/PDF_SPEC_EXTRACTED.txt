APNILEAP INITIATIVE 
Appointment Scheduler Engine 
System Design, Team Feature Contracts, APIs, Sequence Flows and KPIs 
Prepared from Theme — RIT CSE Mini Project Implementation 
Academic Year 2026–27 | Implementation Blueprint | Version 1.0 
Purpose 
Enable four student teams to build independently with explicit boundaries, integrate through versioned 
contracts, and demonstrate measurable end-to-end engineering outcomes for a conflict-free, multi-provider 
appointment booking and scheduling platform. 
Source basis: RIT CSE Theme mini-project format (four-team academic ownership — OS, Data Structures, DBMS, Web Technology) 
1. Executive Design Summary 
Recommended system boundary 
Team D is the user-facing experience and backend-for-frontend; Team C is the authoritative workflow and 
data owner; Team A and Team B are independent computational services. Cross-team communication uses 
versioned HTTPS/JSON APIs and a shared correlation ID. 
1.1 Design objectives 
● Preserve the four-team academic ownership model while making interfaces independently testable. 
● Separate transactional authority (Team C) from algorithm engines (Teams A and B) and 
presentation/orchestration (Team D). 
● Make every booking traceable across all services using appointment_id, request_id, search_id and 
correlation_id. 
● Assess artefacts and engineering evidence — not only whether the final screen appears to work. 
● Allow scheduling-policy and availability-search algorithm variants to be swapped without breaking 
consumers. 
1.2 Key architectural decisions 
Decision Design rule 
Database ownership Team C alone writes the authoritative relational database. Teams A, B and D use APIs; direct cross-team SQL is avoided to reduce coupling. 
Orchestration Team C owns the appointment state machine; Team D orchestrates the user experience but does not become the system of record. 
Algorithm isolation Teams A and B expose deterministic request/response contracts with algorithm_version and test evidence. 
Live updates Team D consumes a Server-Sent Events or WebSocket stream for state changes; ordinary commands remain REST calls. 
Failure handling Every cross-team command is idempotent; Team C records compensation when a slot lease, database commit, availability search or notification step fails. 
2. System Architecture 
=== PAGE 2 ===
 
Synchronous path: HTTPS/JSON for commands and queries; API contracts are versioned under /api/v1. 
Asynchronous path: SSE/WebSocket for dashboard freshness; Team C uses an outbox/audit record so committed 
state changes are not lost. 
Security baseline: Authenticated user session, role-based authorization, TLS, input/schema validation, rate limits, 
audit logging and no database credentials in the browser. 
3. Cross-Team Interface Standards 
3.1 Common request contract 
Field / header Required behavior 
Authorization Bearer token or trusted service credential; every endpoint authorizes the action. 
X-Correlation-ID One ID generated at Team D or Team C and propagated through every service and log. 
Idempotency-Key Required for booking, rescheduling and other create/commit operations. 
X-API-Version Optional header; URI /api/v1 remains the primary version boundary. 
Content-Type application/json; UTF-8. 
Timestamps ISO 8601 UTC; UI may localize for display. 
Identifiers Opaque stable strings/UUIDs; never reuse a database row number as a public contract. 
3.2 Standard response envelopes 
Success: {"data": {...}, "meta": {"correlation_id": "...", "api_version": "v1"}} 
Error: {"error": {"code": "SLOT_CONFLICT", "message": "...", "details": [...]}, 
"meta": {"correlation_id": "..."}}

4.1. Team A — Booking Queue & Slot Scheduling Engine 
Operating Systems Engine 
Mission 
Accept appointment-booking requests, place them in policy-driven queues, allocate available provider slots 
safely under concurrency, and publish scheduling state and performance metrics. 
Feature ownership and contracts 
A1. Request intake and queue management 
Required inputs: request_id, user_id, provider_id, service_type, duration_minutes, priority, submitted_at, 
preferred_window 
Expected outputs: queue_position, state (QUEUED/READY), estimated_start, accepted_policy, correlation_id 
API(s) exposed: POST /api/v1/scheduling/requests; GET /api/v1/providers/{providerId}/queue 
Implementation note: Validate provider capacity and enqueue atomically. Queue implementation may vary by 
algorithm: FIFO, circular queue, priority queue, or heap. 
A2. Scheduling-policy execution 
Required inputs: queue snapshot, provider calendar, selected policy (FCFS/EARLIEST_FIT/PRIORITY/URGENCY), 
quantum_ms, policy parameters

Expected outputs: decision_id, selected_request, assigned_slot_id, scheduled_start, algorithm_version, 
decision_metrics 
API(s) exposed: POST /internal/v1/scheduler/run; GET /api/v1/scheduling/decisions/{decisionId} 
Implementation note: Make policy selection configurable so experiments can compare waiting time, turnaround 
time, utilization, throughput and fairness. 
Team A feature contracts — continued 
A3. Concurrency, lock and double-booking control 
Required inputs: slot_id, holder_id, lock_mode, wait-for edges, lease_timeout, allocation intent 
Expected outputs: lock_granted, lease_id, conflict_reason, deadlock_cycle, prevention_or_recovery_action 
API(s) exposed: POST /internal/v1/locks/acquire; DELETE /internal/v1/locks/{leaseId}; POST 
/internal/v1/deadlocks/analyse 
Implementation note: Use mutex/semaphore simulations and a wait-for graph. No two active bookings may own 
the same exclusive provider slot. 
A4. Runtime state and telemetry 
Required inputs: request state changes, simulated queue processing time, batch completion, cancellation or 
timeout 
Expected outputs: request state, queue depth, utilization, wait/turnaround time, throughput, 
starvation/deadlock indicators 
API(s) exposed: GET /api/v1/scheduling/requests/{requestId}; GET /api/v1/metrics/scheduling; GET 
/api/v1/stream/scheduling 
Implementation note: Expose read-only state to Team D and scheduling decisions to Team C; use Server-Sent 
Events or WebSocket only for the live dashboard stream.

● Scheduling API controller and request validator

● Pluggable scheduling-policy strategy (FCFS, Earliest-Fit, Priority and Urgency-weighted) 
● Slot lease, semaphore/mutex and wait-for-graph manager 
● State-transition publisher and metrics/benchmark collector

4.2. Team B — Availability Search & Conflict Analytics Engine 
Data Structures Engine 

=== PAGE 6 ===
Mission 
Model each provider's calendar as an interval-indexed structure and return deterministic, measurable free-
slot search results, ranked options and conflict/overlap analytics for booking and rescheduling. 
Feature ownership and contracts 
B1. Provider calendar and interval registry 
Required inputs: provider_id, working_hours, blocked_interval (start, end, reason), capacity, status 
Expected outputs: calendar_version, accepted/rejected changes, validation errors, coverage summary 
API(s) exposed: PUT /internal/v1/calendars/{providerId}/intervals; GET /api/v1/calendars 
Implementation note: Support an interval-tree implementation as the baseline and a sorted-array binary-search 
implementation for comparison experiments. 
B2. Free-slot search and ranking 
Required inputs: provider_id, date_range, duration, algorithm (INTERVAL_TREE/BINARY_SEARCH/SWEEP_LINE), 
optimization_metric, constraints 
Expected outputs: search_id, ranked_free_slots, total_options, tie_break_rule, algorithm, 
explored_interval_count 
API(s) exposed: POST /api/v1/availability/search; GET /api/v1/availability/{searchId} 
Implementation note: Reject malformed date ranges. Return calendar_version so search results remain 
reproducible after calendar changes. 
Team B feature contracts — continued 
B3. Fast slot lookup and cache optimization 
Required inputs: provider/date key, slot entry, expiry, calendar version 
Expected outputs: slot_status, cached_result, lookup_time_us, cache_hit, index statistics 
API(s) exposed: GET /internal/v1/slot-index/{key}; POST /internal/v1/slot-cache/invalidate 
Implementation note: Use AVL/Red-Black Tree and hash-map variants so students can compare lookup 
complexity and memory cost. 
B4. Conflict detection and utilization analysis 
Required inputs: calendar snapshot, overlap-check algorithm, benchmark size and repetitions 
Expected outputs: overlap_pairs, double_booking_count, utilization_rate, latency distribution, time/space 
complexity evidence 
API(s) exposed: POST /api/v1/calendars/analyse; GET /api/v1/metrics/availability 
Implementation note: Overlap-detection results should be deterministic for a documented interval-comparison 
rule. 
Team B internal building blocks 
● Calendar API and versioned interval repository 
● Interval-tree and sorted-array/binary-search adapters 
● Pluggable search strategy (Interval-Tree scan, Binary Search and Sweep-Line) 
● AVL/Red-Black Tree and hash-based slot-index adapters 
● Version-aware search cache and complexity/benchmark collector

4.3. Team C — Appointment Data & Transaction Manager 
DBMS Engine 
Mission 
Own the authoritative data model and transactional workflow for users, providers, calendars, appointments, 
and audit evidence. 
Feature ownership and contracts 
C1. User, provider and calendar master data 
Required inputs: user profile and role; provider metadata; calendar working hours, capacity, blocked intervals 
Expected outputs: stable IDs, current state, version, validation result and audit metadata 
API(s) exposed: POST /api/v1/users; GET /api/v1/providers; GET /api/v1/providers/{providerId}/calendar; PATCH 
/internal/v1/providers/{providerId} 
Implementation note: Normalize master data to at least 3NF; use constraints and foreign keys as the first 
integrity boundary. 
C2. Booking transaction and conflict control 
Required inputs: appointment_id, user_id, provider_id, service_type, start/end, purpose, idempotency key 
Expected outputs: appointment state, version, conflict reason, selected slot, timestamps and audit_id 
API(s) exposed: POST /api/v1/appointments; GET /api/v1/appointments/{appointmentId}; POST 
/api/v1/appointments/{appointmentId}/cancel 
Implementation note: Use an ACID transaction and explicit isolation/locking strategy. A retry with the same 
idempotency key must not create a second appointment. 
Team C feature contracts — continued 
C3. Slot commit and compensation 
Required inputs: appointment_id, Team A decision_id and lease_id, selected slot, expected appointment version 
Expected outputs: commit_status, committed appointment, new slot state, conflict details, compensation action 
API(s) exposed: POST /internal/v1/appointments/commit; POST /internal/v1/appointments/compensate 
Implementation note: Commit the appointment and slot state together. On failure, release the Team A lease and 
record a compensating event.

5. End-to-End Call Flow 

=== PAGE 13 ===
 
5.1 Flow interpretation and failure behavior 
1. Team D authenticates the user, validates the booking form and generates or propagates correlation_id and 
idempotency key. 
2. Team C validates master data and creates the authoritative appointment workflow. 
3. Team C calls Team A with an independently traceable scheduling request. 
4. Team A returns either a leased slot allocation, a waitlist outcome or a documented rejection. 
5. Team C commits appointment, slot allocation, provider-calendar state, audit and outbox event in one 
database transaction. 
6. Team C requests an availability/conflict check from Team B when the confirmed workflow needs 
rescheduling or overlap evidence. 
7. Team C returns a stable aggregate to Team D; Team D renders the outcome and subscribes to subsequent 
updates. 
8. If commit fails after Team A grants a lease, Team C releases/compensates the lease. If the availability check 
fails, the booking remains valid but availability_status is DEGRADED and retried.
